# 真实成交与策略反馈闭环设计

## 目标

将系统推荐、用户真实成交、后续行情表现连接为可追溯样本，为长线、短线及多 Agent 决策提供历史校准依据。

用户只需要：

1. 在任一推荐条目上选择“加入复盘”。
2. 按成交批次录入买入或卖出的成交时间、成交价格和成交股数。

系统负责保存推荐现场、计算持仓与收益、补齐后续 K 线表现，并生成可供策略 Agent 使用的聚合反馈。

## 设计原则

- 特别关注与交易复盘均不参与股票池筛选，不构成白名单。
- 推荐效果与用户执行效果分开计算，不能把买入时机偏差错误归因给推荐算法。
- 保留原始推荐快照和每笔成交，派生指标可以重新计算，不覆盖原始事实。
- 不用少量样本自动改写规则；策略校准需要样本门槛、幅度上限和版本记录。
- 第一版计算毛收益，不计佣金、印花税、分红、送转股和融资成本，并在界面明确标注。

## 数据模型

### `strategy_trade_case`

一张复盘单代表“一次系统推荐及其后续真实执行”。

主要字段：

- `case_id`：UUID 主键。
- `decision_id`：可空，关联 `investment_decision_history` 中的精确决策。
- `symbol`、`company_name`。
- `source_module`：短线右侧、长线价投、错杀估值、周期试仓、热门追踪等。
- `recommendation_action`、`recommendation_score`、`rule_version`。
- `recommended_price`、`recommended_at`、`recommendation_payload_json`。
- `status`：`PLANNED`、`HOLDING`、`CLOSED`、`CANCELLED`。
- `created_at`、`updated_at`。

同一只股票可以存在多张复盘单，但同一条推荐决策只能建立一张有效复盘单。

### `strategy_trade_fill`

每条记录是一笔真实成交。

主要字段：

- `fill_id`：UUID 主键。
- `case_id`：关联复盘单。
- `side`：`BUY` 或 `SELL`。
- `executed_at`：带时区的实际成交时间。
- `price`：每股成交价格，必须大于零。
- `quantity`：成交股数，必须为正整数。
- `created_at`。

卖出累计数量不得超过买入累计数量。删除或修改历史成交后，系统必须重新计算复盘单状态和所有派生指标。

### `strategy_outcome_snapshot`

保存自动评估结果，允许重复计算并按唯一键覆盖。

主要字段：

- `snapshot_id`：UUID 主键。
- `case_id`。
- `horizon`：`T1`、`T5`、`T20`、`CURRENT`、`CLOSED`。
- `baseline_type`：`RECOMMENDATION` 或 `EXECUTION`。
- `baseline_price`、`evaluation_price`、`evaluation_date`。
- `return_pct`、`max_runup_pct`、`max_drawdown_pct`。
- `status`：`PENDING`、`MATURED`、`UNAVAILABLE`。
- `calculated_at`。

`T1/T5/T20` 按 A 股实际交易日计算，不按自然日计算。

## 计算口径

### 持仓和真实收益

- 当前持仓 = 累计买入股数 - 累计卖出股数。
- 持仓成本采用移动加权平均法。
- 部分卖出时，已实现收益 = 卖出金额 - 卖出股数对应的移动平均成本。
- 浮动收益以最新有效行情与剩余持仓成本计算。
- 累计毛收益 = 已实现收益 + 浮动收益。
- 累计持仓归零后，复盘单自动进入 `CLOSED`。

### 策略收益

策略收益以推荐快照中的每股价格为基准，独立于用户是否成交：

- T+1、T+5、T+20 使用对应交易日收盘价计算收益。
- 最大上涨使用区间最高价相对推荐价计算。
- 最大回撤使用区间最低价相对推荐价计算。
- 交易日尚未到达时状态为 `PENDING`，数据源失败时为 `UNAVAILABLE`，不伪造结果。

### 执行偏差

系统同时展示第一笔买入价相对推荐价的偏离，用于判断收益差异来自策略信号还是用户执行时机。

## 自动评估

- 打开交易复盘页面时，对未成熟或过期结果进行一次刷新。
- Docker 常驻运行时，每个交易日收盘后执行一次增量评估。
- 评估服务通过现有实时 K 线客户端补齐所需行情；获取到的 K 线继续写入 `market_kline_history`。
- 重复执行必须幂等，不重复插入相同观察记录或相同周期结果。
- 外部行情失败只标记本次刷新失败，不删除已有结果，也不阻断成交录入。

## Agent 纠错机制

新增策略反馈上下文，按 `source_module + rule_version + horizon` 聚合：

- 成熟样本数。
- 正收益比例。
- 平均收益和收益中位数。
- 平均最大上涨、平均最大回撤。
- 推荐到实际买入的平均执行偏差。

处理规则：

1. 样本不足 5 条时只展示，不进入 Agent 提示词结论。
2. 样本达到 5 条后，作为带样本量的历史证据注入 Agent 提示词。
3. 同一策略版本达到 20 条成熟样本后，允许生成可靠性修正建议。
4. 自动分数修正最多为 `-5` 到 `+5` 分，不能绕过流动性、停牌、ST、退市和风险否决等硬规则。
5. 每次修正必须记录使用的样本区间、样本量和规则版本，便于回溯。

第一阶段只实现反馈上下文和有上限的可靠性修正，不自动修改 Nacos 中的规则配置。

## API

- `POST /api/trade-cases`：从推荐快照创建复盘单。
- `GET /api/trade-cases`：按状态和股票查询复盘单。
- `GET /api/trade-cases/{caseId}`：查看复盘详情、成交和评估。
- `POST /api/trade-cases/{caseId}/fills`：新增一笔买入或卖出。
- `PUT /api/trade-cases/{caseId}/fills/{fillId}`：修改成交。
- `DELETE /api/trade-cases/{caseId}/fills/{fillId}`：删除误录成交。
- `POST /api/trade-cases/{caseId}/cancel`：取消尚未成交的计划。
- `POST /api/trade-cases/{caseId}/refresh`：主动刷新行情结果。
- `GET /api/strategy-feedback`：查看各策略版本的反馈统计。

所有写接口执行价格、股数、时间顺序、超卖和状态校验，并返回明确的 4xx 错误。

## 页面交互

### 推荐页

各荐股模块的股票条目增加“加入复盘”命令。点击后立即保存当前推荐快照；已加入时显示“复盘中”，避免重复创建。

### 交易复盘页

新增独立导航页面，采用可扫描表格展示：

- 股票、来源模块、推荐动作与推荐时间。
- 状态、当前股数、加权成本、最新价格。
- 已实现、浮动及累计毛收益。
- T+1、T+5、T+20 策略结果。

点击一行后在右侧详情区查看推荐证据、成交时间线和区间表现。录入成交使用弹窗表单，字段为买卖方向、成交时间、每股价格和股数。

页面单独标注“收益未计交易费用”，并对待成熟、行情不可用和录入错误使用不同状态提示。

## 测试与验收

- 数据库：H2 和 PostgreSQL 均可从空库执行 schema，外键和唯一约束有效。
- 服务：覆盖分批买入、部分卖出、全部卖出、超卖拒绝、修改/删除后重算。
- 评估：覆盖 T+1/T+5/T+20 交易日定位、停牌缺口、行情失败和幂等刷新。
- Agent：覆盖样本门槛、聚合口径和 `±5` 修正上限。
- 前端：覆盖创建复盘、录入多笔成交、查看指标、错误提示和移动端布局。
- Docker：重启后复盘单、成交和评估结果仍然存在。

验收时使用一条真实推荐建立复盘单，录入两笔买入和两笔卖出，确认持仓、加权成本、收益、状态及历史结果全部正确。
