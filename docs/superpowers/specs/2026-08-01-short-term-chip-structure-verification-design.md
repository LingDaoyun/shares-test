# 短线筹码结构与双源认证设计

## 1. 目标

在现有短线右侧策略中增加“筹码成本结构”排序因子，优先展示以下候选：

- 历史成交推算的成本筹码集中在相对低位；
- 当前价格刚站上主要成本区，尚未明显远离成本中枢；
- 前期高位套牢筹码经过充分换手后占比下降；
- MA5/MA10、MA20斜率、量价和收盘强度已经确认上升趋势。

筹码因子只改变已合格候选的推荐顺位，不改变现有资格门禁，不得单独把“观望”升级为“加仓/试仓”，也不得因为外部筹码接口失败而阻断整轮扫描。

系统不得把筹码模型表述为真实股东持仓或“主力必然拉升”。统一使用“推算筹码成本”“上方供给压力”“趋势确认”等可验证措辞。

## 2. 已确认口径

采用“Java本地复算 + Tushare外部认证”的双层方案：

1. 东方财富日K和实时行情负责尾盘可用的本地筹码计算。
2. Tushare `cyq_perf`负责最近完整交易日的外部认证。
3. Tushare `cyq_chips`只用于详情补充、夜间抽样复核和研究，不进入14:50前的强依赖链路。
4. 外部源未配置、超时或限流时，本地筹码仍可参与排序，但认证系数降低。
5. 所有阈值、权重、数据源开关和超时均可通过Nacos热配置，并记录规则版本。

## 3. 数据来源与时点

### 3.1 东方财富本地计算数据

扩展现有日K请求字段为：

```text
f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61
```

其中至少保留：交易日、开盘、收盘、最高、最低、成交量、成交额和换手率。`EastMoneyKLine`、历史归档实体和 `market_kline_history` 同步增加换手率字段。

本地模型使用最近120个完整交易日。历史有效换手率覆盖率低于95%、有效交易日少于80个、OHLC异常或价格复权口径不一致时，状态为 `INSUFFICIENT`，筹码贡献为零。

实时尾盘计算在最近完整交易日分布的基础上，使用当日截至数据截止时间的开盘、最高、最低、最新价、成交量、成交额和换手率追加一根“盘中暂定K线”。该结果必须标记为 `INTRADAY_ESTIMATE`，不能伪装成收盘后正式分布。

### 3.2 Tushare外部认证数据

`cyq_perf`提供：

- `trade_date`；
- `cost_5pct`、`cost_15pct`、`cost_50pct`、`cost_85pct`、`cost_95pct`；
- `weight_avg`；
- `winner_rate`。

接口每天18:00至19:00左右更新，因此14:45尾盘扫描只认证最近完整交易日 `T-1`。当日盘中增量始终由本地模型计算。

Tushare Token只允许通过Nacos或运行环境注入，不写入Git、日志、报告或前端响应。客户端应使用受控并发、短超时和按股票/交易日缓存，避免候选数量放大请求。

### 3.3 点时数据约束

实时决策与历史回测必须区分：

- 实时决策可使用截至当前交易日的前复权序列；
- 历史回测必须使用当时已经归档的K线和当时可获得的复权信息；
- 禁止用今天重新计算的前复权历史反推过去信号；
- 所有筹码结果记录 `tradeDate`、`dataCutoffAt`、`observedAt`、数据源和模型版本。

## 4. 本地筹码分布算法

### 4.1 价格桶

在最近120个有效交易日最低价与最高价之间建立150个等距价格桶，最小精度为0.01元。

### 4.2 每日换手衰减

对每个交易日按以下顺序更新：

```text
旧筹码 = 旧筹码 * (1 - clamp(换手率 / 100, 0, 1))
新筹码 = 当日换手筹码在最低价、成交均价、最高价之间按三角形分布加入
```

成交均价优先使用可校验的 `成交额 / 成交股数`，单位不可靠或结果超出当日高低价时回退到 `(开盘 + 收盘 + 最高 + 最低) / 4`。一字板将当日新增筹码放入唯一价格桶。

### 4.3 输出指标

`ShortTermChipSnapshot`至少包含：

- `averageCost`：推算平均成本；
- `cost5`、`cost15`、`cost50`、`cost85`、`cost95`；
- `winnerRatePercent`：当前价以下筹码百分比；
- `overheadChipRatioPercent`：当前价以上筹码百分比；
- `cost70Low`、`cost70High`、`cost70ConcentrationPercent`；
- `cost90Low`、`cost90High`、`cost90ConcentrationPercent`；
- `distanceToAverageCostPercent`；
- `priorHighZoneResidualRatio`：前期高位区残余筹码比例；
- `turnoverSincePriorHighPercent`：最近有效前高之后累计换手；
- `calculationMode`：`COMPLETED_BAR`或`INTRADAY_ESTIMATE`；
- 数据质量、认证状态、认证系数和缺口列表。

“前期高位区”默认定义为最近120日有效前高的90%至100%价格区间。前高必须早于最近5个完整交易日，避免把正在形成的新高误当成旧套牢区。

内部单位统一如下：价格使用元；展示和API中的换手、获利、上方筹码、集中度、成本距离使用0至100的百分点；分布桶权重、认证系数和成本区重合度使用0至1的小数。Tushare字段进入模型前必须显式转换并做范围校验，禁止依靠字段名称猜测单位。

## 5. 筹码结构评分

原始筹码结构分 `chipStructureScore` 范围为0至100，由四项组成：

```text
成本位置       30%
筹码集中度     25%
上方筹码比例   25%
旧高位消化     20%
```

### 5.1 成本位置

- 当前价位于平均成本上方0%至8%为优选区间；
- 低于平均成本说明右侧尚未确认，降低得分；
- 高于平均成本8%至15%逐步降权；
- 高于15%视为获利兑现和追高风险，不再因获利盘比例高而加分。

### 5.2 筹码集中度

- 70%成本区越窄，说明推算成本越集中；
- 默认以 `(cost85 - cost15) / averageCost` 做连续评分；
- 不使用单一固定断点淘汰候选。

### 5.3 上方筹码比例

- `overheadChipRatioPercent`越低，推算上方供给压力越弱；
- 获利筹码过高但价格远离成本中枢时，不认定为惜售，转入追高风险说明。

### 5.4 旧高位消化

结合 `priorHighZoneResidualRatio` 与 `turnoverSincePriorHighPercent`：

- 旧高位残余筹码下降且前高后累计换手充分，给予加分；
- 只出现高换手但高位残余筹码仍集中，不认定为消化完成；
- 缩量穿越旧高位且没有近期放量确认，只作观察。

所有分段阈值必须配置化，并在样本外验证后调整，不能根据单日候选反向修改规则。

## 6. 双源认证

认证比较最近完整交易日的本地结果和Tushare `cyq_perf`：

```text
平均成本偏差 = abs(localAverageCost - externalAverageCost) / externalAverageCost
70%成本区重合度 = 交集宽度 / 并集宽度
获利比例偏差 = abs(localWinnerRate - externalWinnerRate)
```

默认认证状态：

| 状态 | 条件 | 认证系数 |
|---|---|---:|
| `VERIFIED` | 交易日一致；平均成本偏差不超过3%；70%成本区重合度不低于70%；获利比例偏差不超过10个百分点 | 1.00 |
| `SINGLE_SOURCE` | 本地模型有效，但外部源未配置、超时、限流或缺失 | 0.60 |
| `CONFLICT` | 双源交易日一致但关键指标超出容差 | 0.00 |
| `STALE` | 外部或本地基准早于最近完整交易日 | 0.00 |
| `INSUFFICIENT` | 本地K线或换手率质量不足 | 0.00 |

`VERIFIED`只表示两个模型结果在容差内一致，不表示真实股东持仓得到确认。UI文案统一为“筹码模型已认证”。

外部接口错误不得抛出到扫描主链路。系统记录来源、HTTP状态、根因摘要和重试次数，但不得记录Token。

## 7. 短线排序整合

现有技术资格门禁、动作判定和尾盘执行规则保持不变。通过门禁后，供需排序调整为：

```text
rankingScore =
    technicalRankingScore * 45%
  + chipStructureScore * 25% * verificationCoefficient
  + overheadPressureReliefScore * 20%
  + buyPressureScore * 10%
```

约束：

- 筹码结构最多贡献25分；
- `SINGLE_SOURCE`最多贡献15分；
- `CONFLICT`、`STALE`、`INSUFFICIENT`不贡献筹码分；
- 缺失筹码不得用50分等中性值填充；
- 同日所谓“主力资金”权重由45%降至10%，并继续标注为按成交单量级推算的资金流；
- 排序不得跨越动作层级：可执行候选仍排在观察候选之前；
- 筹码因子不得绕过ST、停牌、流动性、行情新鲜度、严重财务红旗、涨停不可成交、追高和市场压力门禁。

策略版本升级为 `short-term-right-side-v3-chip-verified`。旧历史报告缺少筹码字段时仍可反序列化并显示“历史版本未计算”。

策略支持 `OFF`、`SHADOW`、`ACTIVE`三种激活模式。初次发布使用 `SHADOW`：完整计算、认证、展示并记录V2/V3排序差异，但正式推荐顺序仍由V2决定。样本外验证通过后发布配置切换为 `ACTIVE`，无需重新部署代码。

## 8. 执行时序与缓存

### 8.1 14:30预选

1. 完成全市场行情漏斗和初步技术预选。
2. 对有限候选计算本地T-1筹码分布。
3. 从缓存读取或受控并发获取Tushare T-1 `cyq_perf`。
4. 生成并持久化T-1认证结果。

### 8.2 14:45至14:50尾盘决策

1. 读取已认证的T-1基准。
2. 用当日实时OHLC、成交额和换手率追加盘中筹码增量。
3. 计算当前筹码结构分和认证系数后的贡献分。
4. 在14:50前完成最终排序与快照持久化。

尾盘阶段不得等待Tushare当日数据。外部认证缓存未命中时，立即退化为 `SINGLE_SOURCE`，不能拖过最终输出时间。

### 8.3 收盘后复核

19:10之后可选执行：

- 拉取Tushare当日 `cyq_perf`；
- 将尾盘估算与收盘正式值比较；
- 记录平均成本、筹码区间和排名偏差；
- 为次日模型校准和样本外评估提供数据，但不改写当日已发布决策。

## 9. 持久化与配置

新增 `short_term_chip_verification` 表，主键由股票代码、交易日和模型版本组成，保存：

- 本地与外部摘要；
- 认证状态、系数和差异指标；
- 数据截止时间、观察时间和来源；
- 模型版本与参数指纹；
- 不含密钥的错误摘要。

完整筹码快照同时进入现有短线报告JSON和研究历史，保证推荐顺位可追溯。

Nacos配置前缀：

```yaml
research:
  short-term:
    chip:
      enabled: true
      lookback-bars: 120
      price-buckets: 150
      min-valid-bars: 80
      min-turnover-coverage: 0.95
      weight: 0.25
      activation-mode: SHADOW
      single-source-coefficient: 0.60
      max-average-cost-deviation: 0.03
      min-cost-band-overlap: 0.70
      max-winner-rate-deviation: 0.10
      tushare:
        enabled: false
        base-url: https://api.tushare.pro
        token: ${TUSHARE_TOKEN:}
        connect-timeout-ms: 1200
        read-timeout-ms: 1800
        max-concurrency: 4
```

配置发布时沿用现有校验、版本、试算和回滚机制。Token在配置读取和页面回显时必须脱敏。

## 10. API与页面

候选详情增加“筹码结构”区块，展示：

- 认证胶囊：已认证、单源、数据冲突、数据过期或数据不足；
- 平均成本、当前价距成本中枢；
- 70%和90%成本区；
- 获利筹码、上方筹码、旧高位残余筹码；
- 前高后累计换手；
- 原始筹码分、认证系数和最终贡献分；
- 本地数据日期、外部认证日期和盘中估算标识。

胶囊使用低饱和绿色、蓝灰色、橙色和红灰色，保持对比度但不刺眼。列表只显示认证状态、成本距离和筹码贡献分，完整证据放在详情二级页面。

## 11. 故障与降级

- 东方财富历史换手率缺失：状态 `INSUFFICIENT`，筹码贡献为零，保留原技术候选。
- Tushare未配置或不可用：状态 `SINGLE_SOURCE`，贡献乘0.60。
- 双源冲突：状态 `CONFLICT`，贡献为零，并在风险说明中披露差异。
- Tushare限流：读取最近完整交易日缓存；缓存也无效则单源降级。
- 尾盘剩余时间不足：跳过外部请求，只做本地计算，确保14:50前产出。
- 当前日实时OHLC不完整：只使用T-1正式筹码，标记“当日增量待补”，不伪造盘中结构。

任何筹码故障都不能生成全局 `DATA_BLOCKED`。只有现有全市场行情覆盖、新鲜度或交易门禁失败时，才保持原有阻断行为。

## 12. 测试与验证

### 12.1 单元测试

- 三角形分布、换手衰减、一字板和价格桶边界；
- 换手率0%、100%及异常值；
- 成交均价单位异常时回退OHLC4；
- 成本分位、获利比例、上方筹码和集中度；
- 前高识别、旧高位残余与累计换手；
- 五种认证状态和容差边界；
- 认证系数正确限制筹码贡献；
- 筹码因子不能改变动作层级。

### 12.2 数据客户端测试

- 东方财富 `f61`换手率解析与旧构造器兼容；
- Tushare请求体、代码映射、字段解析、Token脱敏；
- 超时、限流、空响应、错交易日和部分字段缺失；
- 缓存键包含股票、交易日和模型版本。

### 12.3 集成测试

- 预选阶段完成T-1认证，尾盘阶段复用缓存；
- Tushare完全不可用时扫描仍成功并显示单源状态；
- 双源冲突时筹码不加分但候选不消失；
- 已认证且筹码结构更好的同动作候选排名更高；
- 观察候选不能依靠筹码分越过可执行候选；
- `SHADOW`模式只记录V3顺序而不改变正式排序，`ACTIVE`模式才采用V3顺序；
- 旧报告无筹码字段仍可读取。

### 12.4 样本外验证

使用点时数据比较策略V2与V3，至少覆盖多个市场阶段。记录：

- 次日开盘、最高、收盘收益；
- T+1与T+2止盈、止损命中率；
- 最大不利波动和最大有利波动；
- 认证状态分组胜率；
- 筹码贡献分的单调性；
- 扣除手续费和滑点后的收益；
- 行业、市值、涨跌停制度和市场状态分层结果。

V3只有在样本外结果不降低风险调整后收益、且没有显著增加尾部亏损时，才允许替换V2默认排序；否则保留为旁路观察因子。

## 13. 非目标

- 不声称识别真实主力、庄家或具体股东成本。
- 不购买Level-2逐笔数据或商业终端授权。
- 不因筹码集中直接给出买入动作。
- 不用AI修改筹码分、认证结果或规则阈值。
- 不根据单只股票或单日涨跌人工调参。
