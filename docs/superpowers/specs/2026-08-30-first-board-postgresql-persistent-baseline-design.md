# PostgreSQL 单库与首板持久化增量基线设计

## 1. 目标

本设计解决两个已经在真实运行中暴露的问题：

1. 首板页面的 T-1 全市场技术基线只存在 JVM 内存中。API 每次重启都会对全市场逐股重新拉取历史日线，在完成前页面只能显示“基线正在构建”，无法及时给出候选。
2. 系统默认部署仍使用 H2 文件库，不适合作为持续积累全市场日线、技术快照、信号结果和研究历史的长期唯一存储。

最终目标是：

- 将整个系统统一迁移到本机现有 PostgreSQL 17 实例，并完整保留现有 H2 业务数据；
- 最终应用、部署配置和开发配置不再保留 H2 驱动或接入方式；
- 首板模块的历史日线、每日数据完整性、技术基线和构建状态全部持久化；
- 首次基线只构建一次，正常情况下每天只新增最近一个已收盘交易日的数据；
- API 重启后直接读取当前可用基线，不再触发全市场历史重建；
- 当日所需增量不完整或失败时暂停推荐，不使用旧基线兜底。

## 2. 已确认的产品决策

- 这是现有系统内的独立“首板预警”页面，不建设第二套应用。
- 交易日盘中扫描；非交易日使用最近交易日收盘行情继续扫描，不因休市停用页面。
- 创业板和科创板默认排除，但保留页面开关，打开后允许扫描。
- 上一交易日涨停股票仍进入独立观察通道，成交量条件必须合格。
- 页面只展示技术数据，不逐只解释触发原因。
- 只使用页面通知，不增加短信、邮件或外部推送。
- 数据增量或当前基线失败时采用严格关闭：候选列表为空，页面明确显示失败状态，不展示上一份过期推荐。
- PostgreSQL 是迁移后的唯一数据库；完整迁移现有 H2 数据，但最终不保留 H2 的运行接入方式。

## 3. 当前实现与根因

当前 `FirstBoardBaselineService` 的基线保存在 `volatile readySnapshot` 中。构建时先取得全市场股票列表和上一交易日涨停池，再为每只合格股票调用一次历史日线接口，查询 `baselineDate.minusDays(260)` 到 `baselineDate` 的数据。最多 12 个线程并发，所有股票完成后才一次性把内存快照标记为可用。

这带来四个直接后果：

- JVM 重启后没有恢复来源，只能重新执行全市场网络构建；
- 已完成股票的进度没有持久化，中途失败或重启会丢失；
- 页面只能看到笼统的准备状态，无法区分首次导入、每日增量或明确失败；
- 已存在的 `market_kline_history` 是追加式版本流水，当前只有查指纹的写入辅助查询，没有按股票和日期读取最新有效日线的基线接口。

数据库方面，工程已经包含 PostgreSQL 驱动和生产 Profile，但默认 `application.yml`、本地 Profile 和 Docker Compose 仍以 H2 为默认数据源；`apps/api/src/main/resources/schema.sql` 与 `infra/db/init/001_schema.sql` 又分别维护表结构，存在长期漂移风险。

## 4. 模块结构

### 4.1 PostgreSQL 存储模块

PostgreSQL 存储模块向业务代码提供稳定的数据持久化接口，隐藏连接池、批量写入、索引和事务细节。所有现有 JPA Repository 继续使用同一个 Spring Data/JPA 接口，避免为数据库迁移重写业务逻辑。

结构迁移统一由 Flyway 管理：

- `V1` 建立当前正式业务结构；
- 后续版本只通过递增迁移文件修改结构；
- Spring SQL 自动初始化关闭；
- `infra/db/init` 不再维护第二份完整业务建表脚本，只保留数据库实例启动所需的最小初始化，或在不需要时删除。

最终运行包移除 H2 依赖，默认和生产配置都只接受 PostgreSQL JDBC URL。缺少 PostgreSQL 配置时应用启动失败，不静默回退到内存数据库。

### 4.2 首板基线模块

首板基线模块拆成四个职责明确的深模块：

1. `DailyBarStore`：提供规范日线的批量写入、日期覆盖检查和滚动读取接口。
2. `MarketDayIngestion`：协调首次导入、每日增量、漏日补齐和数据完整性状态。
3. `BaselinePublisher`：从本地规范日线计算技术指标，并以事务方式发布不可变基线。
4. `BaselineAccess`：只返回与扫描日期、基线日期和规则版本完全匹配的 READY 基线。

网络行情提供方位于 `MarketDayIngestion` 外侧。技术指标计算只依赖 `DailyBarStore`，因此规则升级可以完全使用本地数据重算，不再次下载历史日线。

## 5. PostgreSQL 数据模型

### 5.1 `first_board_daily_bar`

保存每只股票每个交易日的唯一规范日线：

- `symbol`
- `trade_date`
- `open_price`
- `close_price`
- `high_price`
- `low_price`
- `volume`
- `amount`
- `turnover_rate`
- `adjust_mode`，当前固定为 `QFQ`
- `was_limit_up`
- `limit_up_confirmed`
- `source_name`
- `content_hash`
- `observed_at`
- `updated_at`

主键为 `(symbol, trade_date)`。核心 B-tree 索引为 `(symbol, trade_date DESC)`。同一股票同一日期再次写入时，只有内容摘要发生变化才更新，保证任务可重复执行。

该表只保留首板扫描确实需要的最近 120 个交易日。现有共享表 `market_kline_history` 仍完整保留，不纳入首板清理。120 个交易日覆盖当前 60 根最低指标窗口、20 日图表和复权修复缓冲，同时让该模块的数据量稳定在约 60 万根日线。

### 5.2 `first_board_market_day`

记录每个交易日的数据完整性：

- `trade_date` 主键
- `status`：`IMPORTING`、`READY`、`FAILED`
- `expected_symbol_count`
- `written_symbol_count`
- `failed_symbol_count`
- `limit_up_pool_complete`
- `source_trade_date`
- `started_at`
- `completed_at`
- `error_summary`

只有全市场覆盖满足门槛、交易日期一致且涨停池状态明确时才能进入 READY。基线发布不得通过统计日线行数自行猜测某日是否完整，必须依赖该记录。

### 5.3 `first_board_baseline_run`

记录一次不可变基线构建：

- `run_id` UUID 主键
- `scan_trade_date`
- `baseline_trade_date`
- `rule_version`
- `bar_data_version`
- `status`：`BUILDING`、`READY`、`FAILED`
- `universe_count`
- `supported_count`
- `excluded_name_count`
- `insufficient_history_count`
- `item_count`
- `started_at`
- `published_at`
- `error_summary`

查询方要求扫描日期、基线日期、规则版本和日线版本全部匹配。构建中的 run 不可见；所有条目写入完成后，在同一事务中将 run 发布为 READY。

### 5.4 `first_board_baseline_item`

保存每只股票在某次基线中的技术状态：

- `run_id`
- `symbol`
- `company_name`
- `industry`
- `board`
- `baseline_date`
- `previous_close`
- `ma10`
- `ma20`
- `ma20_slope`
- `rsi14`
- `macd_histogram`
- `technical_pass_count`
- `previous_day_volume_ratio`
- `recent_five_max_volume_ratio`
- `upper_shadow_ratio`
- `three_day_close_range`
- `previous_limit_up`

主键为 `(run_id, symbol)`，并建立 `(symbol, baseline_date DESC)` 索引。K 线图和明细不在条目中重复保存数组，而是从 `first_board_daily_bar` 按日期窗口读取。

### 5.5 现有历史表

`market_kline_history` 继续作为原始版本流水保留，不能用规范日线表替代或删除。它增加适合 PostgreSQL 的 `(symbol, trade_date, observed_at DESC)` B-tree 索引和按日期顺序扫描的 BRIN 索引。

第一阶段不引入 TimescaleDB、分库或自动分区。当前预计数据量下，PostgreSQL 原生表、批量写入、联合索引和正常维护足够。只有单张高增长历史表实际达到数千万行并出现可测量的维护或查询问题时，才按交易年份分区。

## 6. 首次基线建立

首次 PostgreSQL 切换后执行一次可恢复的种子流程：

1. 读取 `market_kline_history`，按 `(symbol, trade_date)` 选择 `observed_at` 最新的 `DAY_QFQ` 版本，批量导入 `first_board_daily_bar`。
2. 获取当前完整 A 股股票全集，排除不支持板块、ST 和退市标识股票。
3. 对每只股票检查至少 60 根有效历史以及指标所需字段。
4. 仅对缺失或有效历史不足的股票调用历史日线接口，补齐到当前所需窗口。
5. 获取对应日期涨停池并持久化 `was_limit_up` 状态。
6. 将完整日期标记为 `first_board_market_day.READY`。
7. 从 PostgreSQL 批量读取本地日线，计算并发布首个基线 run。

每日已导入数据和股票进度持续落库。中途失败、容器重启或人工重试都从缺口继续，不重复下载已经完整的数据。

页面在首次过程显示阶段和真实计数，例如：

`首次候选池准备中：1832 / 5120`

在 run 完整发布前候选列表为空。

## 7. 每日增量流程

正常交易日收盘数据稳定后执行一次增量：

1. 取得全市场收盘批次，校验返回是否完整、市场日期是否为目标交易日。
2. 将当日 OHLC、成交量、成交额和换手率批量 upsert 到规范日线表。
3. 获取并确认当日涨停池，更新 `was_limit_up`。
4. 完整性检查通过后，将该交易日标记为 READY。
5. 计算下一交易日所需的 T-1 技术基线，并原子发布新 run。

正常路径只新增最近一个已完成交易日，不再逐股获取 260 个自然日的历史。

调度时间配置化，默认在 15:20 后开始，并允许有限重试。启动时执行一次轻量对账：如果所需交易日和 READY 记录均存在，直接加载基线；如果缺少一天，补当天；如果系统停机多日，则按交易日顺序补齐。所有缺口完成前维持严格关闭。

## 8. 交易日与非交易日语义

- 交易日盘中扫描日期为当天，基线日期为上一交易日。
- 非交易日扫描日期回退为最近交易日，页面使用该日收盘行情；基线日期再回退一个交易日。
- 周五收盘后生成下一交易日所需基线，周末仍可继续展示周五扫描结果。
- 每个请求只接受日期语义完全匹配的 READY run，避免把周四基线或旧规则误用于周一。

## 9. 前复权与数据修复

规范日线固定使用前复权。除权除息可能改变历史前复权序列，因此每日增量同时检查：

- 当日行情昨收与本地上一交易日收盘的连续性；
- 行情涨跌幅与本地价格推导结果的偏差；
- 同一日期新旧内容摘要是否变化。

检测到显著不一致时，只将受影响股票标记为需要修复，重新获取其指标窗口历史并覆盖规范日线。修复完成前，当日 `first_board_market_day` 不进入 READY，也不发布新基线。全市场历史不会因单股复权变化而重建。

## 10. 状态与失败行为

页面状态映射如下：

- `INITIALIZING`：首次日线导入或首次基线计算；显示阶段和完成计数。
- `UPDATING`：补充最近交易日或生成新基线；候选为空。
- `READY`：只返回当前日期和当前规则版本的候选。
- `FAILED`：显示失败日期、简短错误和最近重试时间；候选为空。

旧 READY run 保留用于审计和重新计算，但访问模块不会在当前增量失败时回退使用。重试创建新的 run，不修改已经发布的条目。

## 11. 页面与接口变化

现有页面布局、板块开关、候选技术字段和页面通知保持不变。快照响应增加：

- 当前数据阶段；
- 目标扫描日期和基线日期；
- 总股票数、已完成数和失败数；
- 当前规则版本；
- 最近成功发布时间；
- 失败摘要和下一次重试时间。

页面不新增逐股触发原因。技术明细仍展示长上影、成交量、横盘区间、均线、RSI、MACD、换手率等现有技术数据。

## 12. H2 到 PostgreSQL 的一次性迁移

### 12.1 迁移范围

以迁移时真实 H2 数据库的用户表清单为准，而不是只依赖任意一份静态 SQL。迁移必须包含行情历史、短线信号、验证结果、自选和观察池、交易复盘、AI 分析与决策历史、运行配置以及所有其他实际业务表。

### 12.2 迁移执行

迁移使用独立的一次性迁移程序：源端以只读方式打开 H2 文件，目标端连接全新 PostgreSQL，按外键顺序分批读取和批量写入。该程序允许重复运行并记录每张表进度，但不进入最终 API 镜像，也不作为最终系统功能保留。

切换顺序：

1. 记录当前容器、镜像、H2 卷和数据库文件位置。
2. 停止 API 写入。
3. 创建 H2 文件级备份和校验摘要。
4. 在本机现有 `postgres:17` 容器中创建独立 `aistock` 数据库，执行 Flyway 正式结构；不安装或启动第二个 PostgreSQL 服务。
5. 分批迁移全部业务表。
6. 校验数据并修正 identity/sequence 到现有最大 ID 之后。
7. 启动只连接 PostgreSQL 的最终 API 镜像。
8. 验证健康状态、关键页面和首板基线恢复。

### 12.3 迁移校验

每张表必须校验：

- 源端和目标端总行数；
- 主键总数、重复数和分批有序摘要；
- 最早与最晚业务时间；
- 关键数值列的空值数、总和或分布摘要；
- 外键孤儿记录；
- identity/sequence 当前值；
- `runtime_config_section` 等运行配置是否完整。

任一表校验失败时不得切换。迁移完成后的 H2 物理备份暂时离线保留为回滚证据，但 Compose、应用依赖、配置和最终镜像均不再提供 H2 连接路径。业务验收完成后再单独决定是否删除备份和旧命名卷。

## 13. 本机 PostgreSQL 与运行配置

- 复用本机已经运行的 `postgres:17` 容器和 5432 端口，不在本项目 Compose 中声明 PostgreSQL 服务或新数据卷。
- 在现有实例内创建独立 `aistock` 数据库和最小权限账号，不复用 `geo_flow` 业务库。
- 宿主机开发连接 `127.0.0.1:5432`；Docker 内 API 连接 `host.docker.internal:5432`。
- API 启动时由 Flyway 校验/升级结构；数据库不可用时启动失败并由现有重启策略重试。
- 数据库名称、用户和密码通过环境变量传入；正式密码不得写入仓库。
- API 移除 `/data` H2 卷挂载和所有 `jdbc:h2:` 默认值。
- `application-local.yml` 同样指向 PostgreSQL，不保留 H2 控制台。
- Maven 移除 H2 runtime 依赖；H2 专用测试迁移为 PostgreSQL 集成测试或纯 SQL 结构测试。
- README 和运行文档只描述 PostgreSQL 路径。

## 14. 性能、事务与空间回收

- 日线按交易日批量写入，避免逐行事务。
- 基线计算按股票分片读取最近窗口，避免加载整张历史表。
- `first_board_baseline_item` 批量插入 BUILDING run，发布状态更新与完整性计数校验位于同一事务。
- 页面读取固定 READY `run_id`，不会在一次响应中混合两代基线。
- 重启恢复只查询当天所需 run 和条目，不执行网络历史构建。
- PostgreSQL 连接池大小、批量大小和并发数通过真实运行指标调整，不以提高线程数代替批量数据路径。
- 每次新交易日数据和下一扫描日基线全部 READY 后执行首板专属清理；清理不能早于原子发布。
- `first_board_daily_bar` 保留最近 120 个不同交易日，删除更早日线。
- `first_board_baseline_run` 与级联条目保留最近 5 个不同扫描日；BUILDING run 永不被清理任务删除。
- `first_board_market_day` 保留最近 130 个交易日的轻量状态，支持缺口识别与清理截止日期计算。
- 清理不触碰 `market_kline_history`、交易复盘、运行配置或其他模块数据。
- 日常 DELETE 后依靠 autovacuum 回收死元组供后续写入复用；不每日执行会锁表的 `VACUUM FULL`。

## 15. 验证与验收

### 15.1 数据库迁移

- 全新 PostgreSQL 可从空库执行所有 Flyway 迁移。
- 全部 H2 业务表迁移并通过逐表校验。
- 最终应用依赖树、配置和镜像中不存在 H2 驱动或 JDBC URL。
- API 只能连接 PostgreSQL，缺少数据库时明确启动失败。

### 15.2 首次建立

- 可复用现有历史版本数据，网络只补缺口。
- 中途失败并重启后从持久化进度继续。
- 首个 READY run 发布前不返回候选。
- 页面显示实际阶段和完成数量。

### 15.3 每日增量

- 正常交易日只新增一个交易日的数据。
- API 重启不触发全市场历史日线请求。
- 漏一天和漏多天均按日期顺序补齐。
- 增量失败时候选为空，不返回上一份推荐。
- 规则版本变化时使用本地日线重算，不下载完整历史。
- 除权除息只刷新受影响股票。

### 15.4 页面行为

- 交易日盘中和非交易日日期语义正确。
- 创业板、科创板开关保持默认关闭且可独立开启。
- 上一交易日涨停股票保留在独立观察通道，成交量门槛继续生效。
- 页面只展示技术面和页面通知，不出现逐股触发原因或外部推送。

## 16. 非目标

- 不为首板模块创建第二个数据库或独立微服务。
- 不引入 Redis 作为基线事实来源。
