# 架构设计

## 目标

这个平台的第一目标不是自动交易，而是把长线投研流程产品化、证据化、可复盘：

```text
全 A 证券主数据与实时行情
-> 流动性/ST/亏损/横盘等资格过滤
-> 政策、公告、财报、K线与行业热度证据
-> 长线价值或短线右侧多因子模型
-> 风控门禁与多 Agent 反证
-> 推荐结果或特别关注主动分析
-> K线、分析和决策历史复盘
```

## MVP 服务边界

当前用模块化单体承载核心业务，避免一开始拆成过多微服务。

```text
apps/api
  policy     政策主题与产业链
  company    公司画像与证据链
  rule       规则引擎、规则配置、试算
  portfolio  特别关注与长线主动分析
  universe   全 A 动态候选漏斗
  shortterm  右侧结构、热度、量能和尾盘验证
  history    K 线版本、分析快照与决策历史
```

后续按压力和团队边界拆分：

```text
market-data-service
document-service
policy-service
company-service
factor-service
rule-engine-service
backtest-service
ai-workflow-service
ai-agent-service
```

当前 MVP 保持模块化单体，不引入服务发现。只有在团队边界、独立扩缩容或故障隔离形成实际需求后才拆分服务，并在届时按部署平台选择服务发现方案。大模型和政策源的动态配置直接存入业务数据库，不增加独立配置中心。

## 点时与历史原则

- 推荐股票不使用静态白名单，特别关注也不参与全市场排名。
- 交易中行情必须通过交易日期和市场时间戳校验；过期行情只能复核，不能形成短线执行建议。
- 休市日只展示最近收盘快照，不标记为实时行情。
- K 线按内容指纹追加保存，源数据修订不会覆盖旧观察版本。
- 主动长线分析和自动短线候选都保存完整 payload、规则版本、数据截至时间与记录时间。
- 历史决策只作为一致性检查和样本依据，不能用旧结论覆盖当前证据。

## 推荐交易复盘闭环

推荐页面的“加入复盘”只捕获已经生成的推荐事实，成交和结果在独立 Hash 路由 `#/trade-review` 操作；它不参与全 A 候选生成、推荐排序或特别关注。五个推荐控制器只使用价格对应的源 `marketTimestamp` 签发短期内存凭证，报告生成时间不能代替行情事实时间；缺失、未来、超过新鲜度边界或被实时门禁阻断的行情不签发。创建接口只接收凭证并从服务端注册表恢复规范快照。客户端不能注入股票、来源模块、动作、规则版本、价格、时间或 payload。案例按规范快照指纹幂等创建，迁移前的未认证案例仍可维护，但不进入 Agent 反馈。

案例可附加任意多笔按时间排序的 `BUY`/`SELL` 成交事实。每笔必须有方向、成交时间、正价格和正整数数量，且成交时间受推荐时间和服务器时钟边界约束。原始成交表只追加；编辑写入 `CORRECTION`，删除写入 `VOID`，每个事件在父案例行锁内分配单调 `revision_sequence`，数据库唯一索引阻止同序号写入。投影器只按该序号重放当前有效版本，不依赖时间戳精度或 UUID。账本在买入时按持仓数量移动加权平均成本，在卖出时按当前平均成本确认已实现毛收益；任何会使持仓为负的卖出都以 4xx 拒绝。持仓和累计收益只计算成交价格与数量，不计佣金、印花税、分红、送转股，因此不是净 P&L。

结果快照与事实分离，可重复刷新而不复制同一“基线类型 + 期限”的记录：

```text
推荐基线：CURRENT / T1 / T5 / T20
执行基线：CURRENT（仍持仓）/ CLOSED（已平仓）
```

`T1/T5/T20` 从上海时区推荐日之后的实际交易日 K 线行计数。历史行情网关返回“行数据 + Provider + 完整性 + 失败说明”；空分片、解析行数不一致、重复交易日或首尾日期覆盖不足都会 fail closed，再尝试另一 Provider 完整回退。未达到所需交易行时为 `PENDING`，空响应、部分响应或 Provider 故障为可恢复的 `UNAVAILABLE`，已成熟的固定期限快照不会被降级。任何成交变化都会把案例持久化为 `outcome_dirty` 并隐藏旧执行结果；成功重算后才清除标志。手动接口可刷新单一案例，调度器在工作日 `Asia/Shanghai 18:10` 优先处理 dirty 案例，再处理普通有界批次。

复盘列表由数据库完成状态/股票过滤，并以 `createdAt + caseId` 做有界 keyset 分页；Criteria 查询通过 `setMaxResults` 返回 `List`，不执行全量 count。前端把实体缓存、首屏初始化和服务端页游标分开，单条捕获或详情读取不能跳过第一页。成交和结果按页批量加载。复盘历史的反馈队列按 `sourceModule + ruleVersion` 隔离，只使用服务端认证且已成熟的推荐 `T20` 结果，并采用有界样本窗口和短时缓存。5 个样本后可作为受限的 Agent 提示词上下文，20 个样本后才产生 `-5..+5` 的可靠性调整。历史反馈不能自动修改数据库运行配置、确定性共识分，或绕过既有硬风控门禁。

本地 Docker 使用挂载在命名卷上的 H2 文件库，复盘案例、成交和结果随 API 容器重启保留。生产/联调可切换 PostgreSQL；共享 schema 同时覆盖两种数据库，避免复盘表出现环境分叉。

## AI 框架选择

主链路优先使用确定性 Workflow：

```text
采集 -> 解析 -> 抽取 -> 入库 -> 因子计算 -> 规则评分
```

Spring AI Alibaba 适合 Workflow-first 场景；AgentScope Java 适合 Agent-first 场景。因此：

- MVP：Spring Boot 服务内封装模型调用与结构化输出。
- 二期：新增 `ai-agent-service`，用 AgentScope Java 做开放式深度研究。
- 任何 Agent 输出都只能进入证据层，不能绕过规则引擎直接产生买卖决策。

## AI 趋势分析节点

政府规划文件和产业报告分析是平台的关键 AI 节点。这个节点不做简单摘要，而是输出可审计的长期趋势假设：

```text
原文证据
-> 显性政策/产业信号
-> 多 Agent 交叉验证
-> 隐含趋势推导
-> 产业链环节拆解
-> A 股公司筛选画像
-> 监控指标
-> 反证条件
```

当前已提供 Prompt 预览接口：

```text
GET  /api/ai/trend-prompts/sample
POST /api/ai/trend-prompts/preview
POST /api/ai/trend-analysis
GET  /api/ai/llm-config
```

真实分析接口使用数据库运行配置中的大模型 Provider。每次模型调用开始时读取一次不可变配置快照；模型输出只进入证据层和趋势层，并包含政策原文核验、产业链机制、数据验证、风险反证、A 股映射和裁判汇总等交叉验证结论，再由规则引擎决定是否进入观察池。

## 当前真实数据源

MVP 已接入以下公开数据源：

```text
中国政府网、发改委、工信部、科技部、财政部、能源局、证监会等多官方政策源
腾讯 A 股实时行情
东方财富 A 股实时行情备用源
东方财富数据中心年度财务指标
```

这些数据用于候选池、政策信号、估值初筛、年度质量规则和观察池生成。公告 PDF 已支持少量在线正文解析；完整问询函、处罚、质押、主营构成等证据仍适合继续扩展为批处理文档库。

## 规则生命周期

```text
编辑规则
-> JSON Schema/业务校验
-> 当前股票池试跑
-> 历史回测预览
-> 生成新版本
-> 发布
-> 数据库版本提交后生效
-> 评分结果记录 rule_version_id
```

## 风控原则

- 硬规则负责排除：退市风险、监管处罚、现金流异常、质押异常等。
- 软规则负责评分：ROE、现金流质量、研发强度、估值分位等。
- 组合规则负责仓位：单股、单行业、单主题、最大回撤、估值过热降权。

## 统一决策中枢

短线、长线、周期和错杀估值使用不同的交易哲学，不能互相套用同一套买卖规则：

```text
短线右侧：市场情绪、热门方向、量价结构、尾盘承接优先，PE/PB 只作低权重风险语境
长期价投：行业地位、盈利质量、现金流、分红、同业/历史估值优先，短期换手和情绪只作辅助
周期试仓：产品价格、产能出清、成本曲线、周期位置和分批仓位计划优先
错杀估值：热门方向过热后的风格切换、优质资产回撤和基本面未恶化证据优先
```

各模块仍然独立输出自己的 `TradingAdvice`，但同一只股票在多个模块同时出现时，必须先进入 `StrategyDecisionBroker` 合议后再展示每日融合建议。Broker 不重新发明选股模型，只处理最终口径：

- 任何减仓或退出信号优先于新增仓位。
- 多个策略同时支持且没有补证门禁，才允许展示“分批加仓”。
- 一个策略支持加仓、另一个策略要求补证或等待时，降级为“轻仓试错”或“观望”，并把分歧来源写入理由。
- 通用全市场、长线、周期和短线结论不能互相覆盖；历史复盘反馈只能调节置信度，不能绕过硬风控。

短线市场状态在“冰点/混沌”和“发酵”之间新增 `结构性行情`：当全市场涨跌广度偏弱，但某一行业形成足够样本、上涨占比、平均涨幅和成交额支持的热点簇时，不再把所有右侧候选一刀切阻断；系统只允许围绕该热点方向按尾盘确认做轻仓试错，不能扩展成全市场追涨。

长线价投质量分在最新年报之外增加持续性证据：近 3-5 年 ROE 不低于 8% 的年份数、经营现金流为正年份数、营收增速连续性、毛利率波动范围和连续分红。单年 ROE 或净利润高增长不能直接打满质量分；如果历史现金流或盈利持续性不足，候选仍可研究，但会标记为“盈利持续性待验证”。

### 长期价投行业模板与逻辑纪律

长期价投使用 `long-term-value-discipline-v1` 五因子模型：

- 盈利质量与现金含金量 30%；
- 行业地位与护城河 25%；
- 估值隐含预期 25%；
- 资本配置 10%；
- 风险与证据质量 10%。

普通企业使用五年 ROE 中位数、现金/利润代理和经营者收益反向 DCF；农业养殖、
资源、钢铁、化工、航运等周期行业使用包含亏损年份的完整周期平均盈利和更高安全边际；银行、保险、
证券等金融行业使用 PB-ROE/剩余收益代理，不套用普通企业经营现金流模型。

当前年度指标缺少资本开支，所以页面明确标注“经营者收益代理”，不能把输出区间
解释成严格自由现金流目标价。资产负债率、利息保障倍数、债务到期结构以及银行的
不良率、拨备和资本充足率缺失时，模型降低证据质量并列出补证项，不用 0 分伪装成
公司质量差。

仓位纪律继续使用默认单票 10%上限。股价相对买入价下跌 15%只触发强制逻辑复核，
只有原逻辑未证伪、安全边际扩大、现金流和偿债能力未恶化且没有新增治理红旗时，
才允许重新评估加仓。进入建仓复核还必须达到行业模板的目标安全边际；关键证据
未补齐时保持证据待补。当前季度、年度和事件审计先以规则清单展示，未接入持仓与
事件调度前不得描述为自动触发。系统每季度轻审计财务和行业证据，每年深审计护城河、资本
配置与竞争格局，重大公告和治理事件实时触发复核。

周期试仓允许处理牧原这类“利润处在周期底部、PE 可能失真”的股票，但只在价格接近周期低位、PB 未脱离资产底、未破前低且出现低位企稳时给出左侧试仓。输出必须包含首笔 10%-15%、继续下探后的第二笔边界、止损价和周期证伪条件；产品价格、库存、产能、供需、毛利率和经营现金流是必填复核链路，不能用单日拉升替代。

错杀估值采用“四门核验”：热门方向过热或退潮只是背景，仍要同时满足资产质量证据、估值折价、弱势日/缩量企稳价格纪律和足够流动性。四门缺一时只能进入财报或公告复核，不输出加仓；低 PE/PB 只说明可能便宜，不自动说明可以买。

## 研究评分视图

公司详情页和观察池共用同一套 `CompanyResearchView`，避免 AI 摘要、规则评分和观察池阶段相互割裂：

```text
CompanyProfile
-> FilingEvidenceProvider：巨潮公告 / 公司画像降级证据
-> CompanyResearchService
-> 五维评分：TREND / QUALITY / MOAT / VALUATION / RISK
-> 证据分层：政策主题线索 / 行情估值证据 / 公告年报证据 / 订单招投标和财务兑现
-> 公告证据：公告样本 / PDF 正文解析数 / 壁垒线索 / 风险线索 / 兑现线索
-> 正文事件：RISK / MOAT / VALIDATION
-> AgentCommitteeService：政策策略 / 财务质量 / 公告壁垒 / 估值纪律 / 反方风控
-> 阶段标签：WATCH_SAMPLE / EVIDENCE_BUILDING / WAIT_FOR_PRICE / VALUATION_WATCH / RISK_REVIEW
```

其中 `VALUATION_WATCH` 只是观察阶段，不代表买入建议。真正进入交易动作前还需要历史回测、组合风险约束和人工复核。

多 Agent 共识层当前是“确定性投票 + 可选 LLM 论证增强”：每个角色基于同一份研究视图、公告正文事件和风险清单给出投票、置信度、支持证据、反对意见和补证清单。手动触发 AI 增强时，模型只负责补充各 Agent 的论证、反证、信心说明和建议阶段；投票、否决、共识分和默认阶段仍保留在可审计规则里。后续可以把开放式深度研究迁到 AgentScope Java 的 `ai-agent-service`，但模型输出仍只能进入证据层。

Agent 选股会在共识层之上做横向 shortlist：先从全市场公司池抽取复核样本，再逐只运行五 Agent 投票，最后按共识分、支持/观察票、复核/否决票和阶段安全性排序，输出少量候选。每个候选都保留 `UNIVERSE_SCREEN`、`AGENT_DISCUSSION`、`DISAGREEMENT_REVIEW`、`FINAL_SHORTLIST` 四段 trace，前端可查看完整讨论过程。
